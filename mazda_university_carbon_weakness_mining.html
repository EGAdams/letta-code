Team Design Chapter

Weakness Mining Before Proposal Generation

How to integrate Carbon's failure-pattern detection, clustering, and common-cause analysis into Mazda's existing self-improvement system — without rewriting the parts that already work.

Executive conclusion Do not replace Mazda's self-improvement loop. Insert a new weakness-mining subsystem between Judge and Propose. Mazda should stop proposing fixes from a repeated failure label alone. It should first collect failure observations, detect recurrence, build defensible clusters, determine the likely common cause, and create a structured DiagnosedWeaknessCluster. Only that diagnosed object should be eligible to reach MazdaProposalGenerator.

1. What Mazda already has

Mazda's present architecture is already the right foundation. The kernel records a TraceRecord; the evaluation family turns finance evidence into a ScoreCard, a PASS / FAIL / NEEDS_REVIEW verdict, and a finance FailureType; the improvement family generates a reviewable proposal; the experiment runner compares baseline versus candidate; four gates protect safety, cost, regressions, and usefulness; and activation remains human-approved and rollback-safe.

The current proposal milestone already contains MazdaProposalGenerator and FailurePatternSuggester. Its present pattern logic is intentionally simple: repeated failure patterns produce a proposal, and the current tests prove that repeated failure types collapse to one proposal per type.

The gap Carbon exposes A FailureType is a symptom class, not necessarily a root cause. Ten wrong_category failures can come from ten different causes: a missing vendor alias, a mixed-purpose retailer, a stale memory note, a context-selection problem, a misleading tool description, or an ambiguous receipt. Grouping by the label alone is too coarse for safe self-improvement.

2. The new loop: add three stations, not a rewrite

Carbon's weakness-mining idea should be represented explicitly in Mazda's pipeline. The proposal agent should never be the component that decides whether three failures are actually the same problem; that would mix diagnosis and solution generation.

  1. Observe every non-passing run. Convert the trace, scorecard, verdict, and classifier output into a durable FailureObservation.
  2. Detect recurrence cheaply. Use deterministic fingerprints and structured features first. Do not call an LLM merely to notice that the same verifier, field, tool, and workflow stage keep failing.
  3. Build candidate clusters. Group failures that are plausibly the same weakness while preserving the evidence for why they were grouped.
  4. Validate a common cause. Ask whether one mechanism actually explains the cluster. Similar-looking symptoms without a shared cause must be split or rejected.
  5. Check cluster eligibility. Require recurrence, adequate confidence, diversity across cases, and sufficiently low flakiness before improvement work begins.
  6. Generate a proposal from the diagnosed cluster. The proposer receives a cause hypothesis and bounded evidence, not a bag of unrelated failed runs.

3. First new object: FailureObservation

Mazda already preserves traces and verdicts. Weakness mining needs a smaller, normalized record designed for comparison across runs. Think of it as the forensic index card created from a failed run.

3.1 What belongs in the fingerprint?

The fingerprint should describe the shape of the failure, not the accidental particulars of one transaction. A useful first version can hash a canonical tuple such as:

(
    failure_type,
    task_type,
    workflow_stage,
    verifier_code,
    tool_name,
    field_name,
    normalized_error_code,
)

Usually include

  • Failure type
  • Workflow stage
  • Verifier/check that failed
  • Tool or operation involved
  • Field being resolved
  • Normalized error or reason code
  • Agent/minion role when relevant

Usually do not include

  • Exact dollar amount
  • Exact transaction date
  • Trace ID
  • Raw prose wording from the model
  • Vendor name unless the vendor is part of the hypothesized cause
  • Random session identifiers

If exact values are put into the fingerprint too early, every failure becomes unique and no cluster forms. If the fingerprint is too broad, unrelated failures collapse together. Store the detailed values as evidence, but keep the first-stage signature intentionally structural.

4. Failure-pattern detection: cheap code first

The first mining pass should be deterministic and inexpensive. Mazda's existing design already prefers deterministic verification before LLM judgment; weakness mining should follow the same rule.

Recommended trigger After every non-passing verdict, persist the FailureObservation immediately. Then run a cheap incremental pattern check. Only when a candidate pattern reaches an eligibility threshold should Mazda spend tokens on common-cause analysis.

4.1 Suggested detection policy

RulePurposeSuggested initial default
Minimum occurrencesIgnore isolated mistakes3 observations
Distinct tracesPrevent one retry storm from looking like recurrence3 traces
Distinct tasks/documentsFavor real general weaknesses over one corrupted input2 cases where possible
Time windowKeep mining relevant to current behaviorConfigurable; e.g. recent 30–90 days
Wrapper compatibilityAvoid mixing failures from materially different champions without recording that factSame major wrapper family by default
Flake ceilingSet aside nondeterministic noiseConfigurable; do not promote unstable patterns automatically

Those numbers are engineering defaults, not Carbon doctrine. Put them in a versioned MiningPolicy, not in procedural code.

class MiningPolicy(BaseModel):
    version: str
    min_occurrences: int = 3
    min_distinct_traces: int = 3
    min_distinct_cases: int = 2
    lookback_days: int = 60
    max_flake_ratio: float = 0.34
    require_common_cause: bool = True

4.2 Two-pass pattern detection

Use two passes so the cheap system catches obvious patterns and a more capable analyzer is reserved for the residue.

Pass A — exact / deterministic

Group by fingerprint or strict structured compatibility. This catches repeated failures such as the same verifier failure at the same workflow stage.

cheap repeatable

Pass B — fuzzy candidate discovery

For unassigned observations, compare structured features and optionally ask a semantic/LLM strategy whether two groups appear related. This only creates a candidate cluster; it does not prove common cause.

bounded LLM use

5. Clustering: similarity is necessary but not sufficient

Carbon's crucial rule is that repeated failures should be grouped only when they share a real cause. Mazda should therefore distinguish a candidate cluster from a validated weakness cluster.

class WeaknessCluster(BaseModel):
    cluster_id: WeaknessClusterId
    status: ClusterStatus
    observation_ids: list[FailureObservationId]

    dominant_failure_type: FailureType
    fingerprint_family: str | None
    similarity_score: float

    distinct_trace_count: int
    distinct_case_count: int
    flake_ratio: float

    created_at: datetime
    updated_at: datetime

5.2 Hard compatibility filters before fuzzy similarity

Do not compute one giant semantic similarity score over every failure. First apply hard compatibility rules that prevent obviously bad merges.

  • A totals-verification failure should not cluster with a missing vendor key merely because both occurred on the same statement.
  • A tool-routing error and a malformed tool result should remain separate unless evidence shows one causes the other.
  • A failure introduced after a wrapper revision should be marked separately from the same-looking failure under an older revision.
  • A single document that fails repeatedly under retries should not automatically count as several independent occurrences.

5.3 Similarity strategy

class IFailureSimilarityStrategy(ABC):
    @abstractmethod
    def score(
        self,
        left: FailureObservation,
        right: FailureObservation,
    ) -> SimilarityResult:
        ...

The first implementation should be a weighted structured strategy, not an embedding-first strategy. For example:

score =
    0.30 * same_failure_type +
    0.20 * same_workflow_stage +
    0.20 * same_verifier_or_tool +
    0.15 * same_field +
    0.10 * same_normalized_error +
    0.05 * same_document_family

The exact weights belong in a versioned policy and tests. Later, a semantic strategy can be added behind the same interface without changing the mining coordinator.

6. Common-cause analysis: the most important new boundary

A cluster is not ready for Suzuki or any proposal generator until Mazda can state, in structured form, why these failures belong together. This is the difference between “several things went wrong” and “we have identified one weakness worth fixing.”

6.1 Root-cause taxonomy

Use a small, explicit taxonomy. It should map naturally to Mazda's editable surface and existing command objects.

Cause classMeaningLikely improvement target
MEMORY_GAPA stable fact or mapping is missingMemoryNoteCommand
PROMPT_INSTRUCTIONThe instruction is absent, ambiguous, or ordered poorlyPromptPatchCommand
TOOL_CONTRACTTool meaning, parameters, or result interpretation are unclearToolDescriptionPatchCommand
CONTEXT_SELECTIONNeeded evidence exists but is not placed into the working contextContextRulePatchCommand
WORKFLOW_ROUTINGThe wrong agent/tool/path is selectedFuture bounded workflow command or deterministic code strategy
DETERMINISTIC_CODE_GAPThe job should be done by code rather than model judgmentInterface-backed deterministic strategy; usually human-engineered initially
MODEL_CAPABILITYThe weakness persists despite adequate memory/harness supportNot an automatic Mazda wrapper proposal
UNKNOWNEvidence is insufficientNo proposal

6.2 A diagnosis must explain mechanism, evidence, and counterevidence

class CauseHypothesis(BaseModel):
    cause_type: RootCauseType
    summary: str
    mechanism: str

    supporting_observation_ids: list[FailureObservationId]
    counterexample_observation_ids: list[FailureObservationId]

    confidence: float
    editable_targets: list[EditableTarget]
    recommended_test_shape: str

    analyzer_name: str
    analyzer_version: str
Do not accept symptom restatement as diagnosis “Mazda gets categories wrong” is not a root cause. “The categorizer receives merchant-level context but loses line-item descriptions for mixed-purpose retailers, causing the category rule to over-weight the vendor default” is a testable cause hypothesis.

6.3 Deterministic-first cause analysis

Just like Mazda's verdict system, diagnosis should be layered:

  1. Rule-based cause recognizers. Obvious mappings can be recognized without an LLM. Example: repeated missed_vendor_key failures where the vendor exists in the mapping source but is absent from the selected context strongly indicate CONTEXT_SELECTION.
  2. Evidence-bundle builder. Construct a compact bundle of representative failures, their successful near-neighbors, wrapper revisions, tool calls, and verifier evidence.
  3. LLM cause analyzer as fallback. Ask Suzuki or another stronger model for a structured cause hypothesis only when deterministic rules cannot resolve the cluster.
  4. Cause validation policy. Reject hypotheses that lack evidence, contradict cluster members, have low confidence, or merely repeat the failure label.

6.4 Use successful near-neighbors

A cause analyzer should see not only failures but also a few similar cases that passed. These “negative controls” are often what distinguish correlation from cause.

Example

Failures: Check descriptions containing only a check number fail to gain payee information.

Passes: Checks with a matching record in transfer_pay_activity.txt succeed when that file was present in context.

Diagnosis: The likely weakness is not “checks are hard.” It is that the context-building/routing path does not consistently consult the transfer-pay activity evidence before declaring the payee unknown.

7. Recommended contracts: keep the system interface-first

The most maintainable design is to make weakness mining its own bounded subsystem rather than burying new behavior inside MazdaProposalGenerator.

        self,

        ...


class IFailureClusterer(ABC):

    def cluster(
        self,
        observations: Sequence[FailureObservation],

        ...


class ICommonCauseAnalyzer(ABC):

        self,

        ...


class IClusterEligibilityPolicy(ABC):
    @abstractmethod
    def evaluate(
        self,
        cluster: WeaknessCluster,
        cause: CauseHypothesis,
    ) -> ClusterEligibility:
        ...

7.1 The object proposal generation should consume

class DiagnosedWeaknessCluster(BaseModel):
    cluster: WeaknessCluster
    cause: CauseHypothesis
    eligibility: ClusterEligibility
    representative_observation_ids: list[FailureObservationId]
    held_out_observation_ids: list[FailureObservationId] = []

This becomes the new upstream contract for proposal generation. The proposer is no longer responsible for discovering the problem; it is responsible for proposing a bounded change to a diagnosed problem.

8. Factory and persistence changes

8.1 Recommended GoF shape: add an eleventh factory family

Mazda currently separates persistence, evaluation, improvement, reporting, and other concerns into factory families. Weakness mining is neither verdict evaluation nor proposal execution; it is the bridge between them. For Single Responsibility and future reuse by Scissari/Frita, the cleanest architecture is a dedicated family.

class IWeaknessMiningFactory(ABC):
    @abstractmethod
    def create_observation_builder(self) -> IFailureObservationBuilder: ...

    @abstractmethod
    def create_similarity_strategy(self) -> IFailureSimilarityStrategy: ...

    @abstractmethod
    def create_clusterer(self) -> IFailureClusterer: ...

    @abstractmethod
    def create_cause_analyzer(self) -> ICommonCauseAnalyzer: ...

    @abstractmethod
    def create_eligibility_policy(self) -> IClusterEligibilityPolicy: ...

    @abstractmethod
    def create_coordinator(self) -> IWeaknessMiningCoordinator: ...
Lowest-blast-radius alternative If the team wants the smallest initial diff, these creators can temporarily live on IImprovementFactory. But the long-term design should move them to IWeaknessMiningFactory; otherwise the improvement factory becomes responsible for both diagnosing failures and producing changes.

8.2 Changes to IAgentRuntimeFamily

Add a read-only weakness_mining_factory property. The composition root chooses the concrete mining family exactly as it already chooses persistence, evaluation, and improvement. Existing direct-construction paths can remain supported, preserving Mazda's additive factory philosophy.

8.3 Persistence contracts

Weakness mining must be durable. If clustering lives only in memory, Mazda forgets its accumulated evidence on restart and cannot audit why a proposal was created.

class IFailureObservationRepository(ABC):
    def save(self, observation: FailureObservation) -> None: ...
    def list_unassigned(self, policy: MiningPolicy) -> list[FailureObservation]: ...
    def list_for_cluster(self, cluster_id: WeaknessClusterId) -> list[FailureObservation]: ...


class IWeaknessClusterRepository(ABC):
    def save(self, cluster: WeaknessCluster) -> None: ...
    def get(self, cluster_id: WeaknessClusterId) -> WeaknessCluster: ...
    def list_by_status(self, status: ClusterStatus) -> list[WeaknessCluster]: ...


class ICauseHypothesisRepository(ABC):
    def save(self, cluster_id: WeaknessClusterId, cause: CauseHypothesis) -> None: ...
    def history(self, cluster_id: WeaknessClusterId) -> list[CauseHypothesis]: ...

9. Change proposal generation so it cannot skip diagnosis

The present system's critical behavior change should be enforced by the type system and interfaces, not by a comment saying “please mine first.”

9.1 Old contract shape

# Conceptually
proposal = proposal_generator.generate(failing_verdicts)

9.2 New contract shape

class IProposalGenerator(ABC):
    @abstractmethod
    def generate(
        self,
        weakness: DiagnosedWeaknessCluster,
    ) -> ImprovementProposal:
        ...
Compile-time architectural rule A raw VerdictRecord or list of FailureType values should no longer satisfy the main proposal-generator contract. That makes it structurally difficult to bypass mining by accident.

9.3 What to do with FailurePatternSuggester

Do not throw it away immediately. Migrate it in one of two ways:

Preferred

Replace its responsibility with DiagnosedClusterSuggester. It maps a validated cause type to the appropriate proposal/command family.

clean responsibility

Compatibility path

Keep FailurePatternSuggester as a deprecated adapter that accepts only diagnosed clusters and forwards them to the new suggester. Existing imports survive while behavior becomes safer.

low blast radius

10.1 Batch versus immediate mining

The best hybrid is:

  • Immediate: save every observation and perform deterministic fingerprint assignment.
  • Threshold-triggered: when a candidate reaches recurrence criteria, run common-cause analysis.
  • Periodic sweep: occasionally rescan unassigned/noisy observations to discover fuzzy clusters missed by exact fingerprints.

This keeps normal Mazda execution cheap while still letting patterns emerge over time.

This feature is ideal for Mazda's TDD approach. Build the contracts and acceptance tests first; implementation can then be split among agents safely.

12. Safe rollout plan

Implement this in layers so the team can inspect the evidence at each step. Do not connect it to proposal generation on day one.

  1. Phase A — Observation only. Add FailureObservation, builder, repository, schema, and reports. Mazda behavior is unchanged.
  2. Phase B — Shadow mining. Run deterministic fingerprints and clustering, but do not create proposals. Compare clusters with team judgment.
  3. Phase C — Common-cause diagnosis. Add deterministic cause rules and an LLM fallback. Persist diagnoses; still no automatic proposal creation.
  4. Phase D — Eligibility gate. Add recurrence, confidence, diversity, and flake policies. Review what would have been allowed through.
  5. Phase E — Rewire proposals. Change IProposalGenerator to consume DiagnosedWeaknessCluster. Keep human approval and all existing experiment/promotion gates unchanged.
  6. Phase F — Add held-in/held-out partitioning. Once cluster quality is trusted, hide part of each cluster from the fixer so proposal quality is measured on unseen examples rather than memorized cases.
Why this rollout is safe Phases A–D are observational. They can be deployed without changing Mazda's production decisions or wrapper. The first behavior-changing step is Phase E, and even then the existing experiment runner, regression detector, four promotion gates, approval gateway, snapshot, and rollback remain in control.

13.1 Architectural decisions I recommend

  • Create a dedicated IWeaknessMiningFactory rather than making IEvaluationFactory or IImprovementFactory own the entire mining process.
  • Use Pydantic value objects for observations, clusters, policies, evidence bundles, and cause hypotheses.
  • Persist every mining decision in SQLite so a proposal can always answer: “Which failures caused me to exist, and why were they considered the same weakness?”
  • Run deterministic fingerprints and rule-based cause recognizers before any LLM analysis.
  • Keep semantic/LLM clustering as a strategy behind an interface, not as the core definition of a cluster.
  • Require a common-cause hypothesis with supporting evidence before a cluster is proposal-eligible.
  • Treat FailureType as one clustering feature, never as proof that two failures share a cause.
  • Use successful near-neighbor cases as counterevidence during diagnosis.
  • Keep the existing human approval, A/B experiment, regression gate, and rollback system untouched.
  • Introduce held-out examples immediately after the mining layer is trusted, so Suzuki cannot overfit the cases used to describe the weakness.
The mental model to carry forward Mazda should not improve from failures; Mazda should improve from diagnosed recurring weaknesses.
A failure is one event. A pattern is repeated evidence. A cluster is a candidate shared weakness. A common-cause diagnosis explains the mechanism. A proposal is allowed only after that chain exists.
