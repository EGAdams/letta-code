Where the typing earned its keep

Round 9 pointed at the standby credentials bundle and said: check first whether a malformed bundle raises loudly. It does not. It fails in the one direction that cannot be undone.

codex_refresh_candidates exists to make sure a heal never parks a different ChatGPT account's refresh token as the standby. Its guard read: 

account = standby_creds.get('account_id')
...
if account and tokens.get('account_id') != account:
    continue

A bundle that had lost account_id — an empty object, a truncated write, a hand-edited file — did not fail that check. It switched the check off. Verified against the shipped code before the model existed:

heal_standby_token then writes the winning token back over the standby file. Codex refresh tokens are single-use and rotating, so the overwritten one is gone: the failure mode was the dashboard quietly replacing the fleet's only spare account with a token belonging to somebody else's login, and then reporting that spare as dead forever. The old code's own docstring says this is what the guard was for.

access_token is deliberately NOT required. A parked bundle holding only a refresh token is stale, not unusable, and healing it is exactly what this module is for. Requiring it would have deleted a working recovery path while looking like extra safety. The model refuses one field, and it is the one whose absence turns a guard off rather than raising.
Generalising round 9's rule. Round 9 typed a payload that was read. This one guards a value that is written. When you look for the next Pydantic target, prefer the boundary where a wrong value gets persisted: a bad read is wrong until the next poll, a bad write is wrong until a human notices.

Why poll_loop takes a callable

The thread body is poll_loop(poll_once), not poll_loop(provider_name, deps). A daemon thread started at boot would otherwise capture one Collaborators bundle and hold it for the life of the process, which is the exact thing "rebuild the bundle per call" exists to prevent. Taking the sweep as a callable means server's wrapper — and therefore the bundle — is rebuilt on every one of the 90-second iterations. There is a test for it.

One destination, one definition

'adamsl@100.80.49.10' had four independent definitions: hosts.LETTA_DOCKER_HOST, server.CHATGPT_FAILOVER_HOST, chatgpt_provider_accounts.CHATGPT_FAILOVER_HOST, and the ssh calls in ssh_checks. That is how you end up swapping a token on one box and probing another. Both copies now bind hosts.LETTA_DOCKER_HOST, with a test asserting identity. Side effect worth knowing: the failover host is now LETTA_DOCKER_HOST-overridable through the environment, where before it was a literal.

Tests

85 tests in tests/test_chatgpt_failover.py, pointed at the owning module. The 11 superseded copies were deleted from tests/test_server.py / tests/test_provider_usage.py and replaced with pointer comments. Suite: 2,846 → 2,920.

Beyond the moved assertions, the new file pins behaviour nothing covered before:

  • every bundle the model refuses, and the old code parking another account's token from each one — written out as the code that used to run, inline, so the day the model stops earning its keep is visible;
  • a refresh reply with a null access_token keeps the old one rather than parking a null (which would make the standby unprobeable and read as "unusable after refresh" forever);
  • a rotating refresh token is stored — failing to store it leaves the next heal with nothing to try;
  • a capped standby is never healed (a refresh cannot fix a rate limit) and a stale one always is;
  • a failed swap still starts the cooldown, or a broken swap script is retried every 90 seconds forever;
  • the write is temp-then-rename under umask 077 — a half-written standby file is a destroyed standby file, and the swap script can read it at any moment;
  • only chatgpt_oauth failures reach the failover: the Mazda fleet's anthropic row shares this sweep and a Claude rate limit must never swap the ChatGPT token;
  • a Letta outage leaves agent state alone, and a provider with no agents is never probed;
  • the loop survives a sweep that raises, and calls the wrapper it was given each time;
  • and the module state fixture resets the cooldown around every test — _state is process-wide, so without it one test's swap silences the next one's.

How to rank a cluster

The right question is: which names stay behind in server.py after the move? A name referenced only by the cluster travels with it and costs nothing. Counting every top-level name a cluster touches penalises exactly the clusters that are most self-contained. Run this from dashboard/ against the current file before choosing: 

import ast
from collections import defaultdict
src = open('server.py').read(); tree = ast.parse(src)
funcs = {n.name: n for n in tree.body
         if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef))}
top = set(funcs)
for n in tree.body:
    if isinstance(n, ast.Assign):
        for t in n.targets:
            if isinstance(t, ast.Name): top.add(t.id)
refs = defaultdict(set)          # name -> top-level funcs that reference it
for fname, node in funcs.items():
    for sub in ast.walk(node):
        if isinstance(sub, ast.Name) and isinstance(sub.ctx, ast.Load) \
                and sub.id in top:
            refs[sub.id].add(fname)
def deps(name):
    n = funcs.get(name)
    return set() if n is None else {
        s.id for s in ast.walk(n)
        if isinstance(s, ast.Name) and isinstance(s.ctx, ast.Load) and s.id in top}
names = {...}                    # the cluster you are considering
while True:                      # pull in what only this cluster uses
    ext = set().union(*(deps(n) for n in names)) - names
    travels = {x for x in ext if not (refs[x] - names)}
    if not travels: break
    names |= travels
stays = sorted(set().union(*(deps(n) for n in names)) - names)
lines = sum(funcs[n].end_lineno - funcs[n].lineno + 1 for n in names if n in funcs)
print(lines, 'lines |', len(stays), 'stay behind:', stays)
print('cluster members:', sorted(names))

Five caveats, all of them earned

  1. The script counts function bodies, so module-level constants that travel are free lines it does not credit — and the wrappers and explanatory comments left behind cost lines back. Round 10 measured 210 and removed 214. Round 9 measured 285 and removed 374 (a 70-line config literal the script cannot see). Round 8 measured 183 and removed 152. A big config literal in the set means you will beat the estimate; a cluster of pure functions means you will roughly match it.
  2. It cannot see http_app. It parses server.py and nothing else, so every srv.<name> call in the route ladders is invisible to it. Round 8 had seven such names, round 9 had nine, round 10 had zero. Always grep http_app/ for every name you plan to drop. The suite will not catch it: tests/http_app_harness.py stubs the service layer, so those tests pass against a name that no longer exists.
  3. A route reaching into a private name is a design signal, not just an import to preserve. Round 9's four became two verbs and one was fixing a real race; round 10's one poke at _chatgpt_failover['last_note'] became last_failover_note(). Ask what the caller is trying to do before you re-export the pieces it was doing it with.
  4. It cannot tell you a name is mis-clustered. Round 10's record_agent_send_error / clear_agent_send_error were offered as free travellers and would have dragged three cache globals along and broken a route. Round 8's "Document Vision health" 83 lines with zero stays was a mirage over an already-extracted registry. Grep every name you are about to move.
  5. Cluster membership is a judgement — widen or narrow the set and the numbers move.

Standing rules for every round

  1. Extract lowest-residual-coupling first, measured with the script above, not by eye. Then grep every name in your set — the script cannot tell you a name is mis-clustered, and round 10 proves it will hand you names that belong to somebody else's cache.
  2. Grep http_app/ before dropping any name. The script parses server.py only, and the route ladders reach in through srv.<name> at call time. The HTTP tests stub the service layer, so they will not catch a missing name either. Seven in round 8, nine in round 9, zero in round 10.
  3. Point new tests at the owning module, never at server. A re-export is a second binding; the moved code closes over its own module global, so monkeypatch.setattr(server, 'X', …) isolates nothing while looking exactly like it does. This has now bitten seven rounds running.
  4. Inject what stays behind in server.py rather than importing it, and resolve the bundle per call. Add a test that production wires the real collaborators, and one that proves the late binding. A background thread needs extra care: take the sweep as a callable so the bundle is rebuilt per iteration instead of frozen at boot (round 10's poll_loop). A dependency that already has its own module (LETTA_BASE_URL, LETTA_DOCKER_HOST, classify_failure) is imported, not injected.
  5. Import back only what is still called — and re-check the previous round's re-exports, which expire when their last caller leaves (round 10 dropped round 9's _probe_codex_usage). Assert the dropped names are absent so dead re-exports cannot creep back, and assert the kept ones are the owning module's object.
  6. A fake must be pinned to the real thing it fakes. Where a dashboard module fakes a rol_finances object, add one test that runs the path unpatched against the real one. (See the round-6 postscript.)
  7. Deploy and verify against the real thing. Committing is not deploying, and a 200 is not a verification. For a backend-only change, call the moved code on the live box and read the output. If a path cannot be fired safely, say which one and why rather than firing it or pretending it was checked — and find the reversible neighbour that exercises the same machinery (round 10 re-parked an identical standby bundle to prove the ssh write path without touching a token).
  8. Every Pydantic model dumps to a plain dict so browser-facing JSON stays byte-identical, and keep a golden-payload test against the prior literals — error strings included. Better still, run the old code and the new one side by side against the real live values; it is a five-line script and it converts "should be identical" into "is identical". Rounds 9 and 10 both did.
  9. Reach for Pydantic where a wrong value is silent, not everywhere, and prefer the boundary that persists: a bad read is wrong until the next poll, a bad write is wrong until a human notices. The test that proves it earns its keep is the one showing the old code accepting garbage — write that test as the old code, inline, so it keeps being true. And check the predicted defect is actually reachable: round 8's cache model was predicted for a torn read that could not happen and earned its place for an entirely different bug. Require the field whose absence disables a guard; leave optional the field whose absence a recovery path is built to handle.
  10. An error message is an input to something. Before shipping a new failure string, run it through classify_failure() (or whatever downstream reads it) and assert the label, not the text. Also assert the strings that should keep their label still do — scrubbing that goes too far turns a real rate limit into a generic error.
  11. Stay out of js/ — unless the bug is there. A concurrent dashboard-boot.js refactor runs in parallel; an earlier round saw tests/test_project_plans.py fail on its edits, not ours. Confirm with git status js/ before blaming yourself. Rounds 9 and 10 touched nothing there.

Where Pydantic mattered, cumulatively

  • ModelStatSource.kind: Literal['codex','claude','gemini'] — a typo used to render a card with no windows and no error.
  • PcMonitor.memory_source: Literal['windows','linux'], frozen=True for the process-wide registry.
  • PcMetric derives alert from level as a property, so a new level can't be added without deciding whether it blinks the tab.
  • ProbeResult.hard — suppresses the Restart button for failures a restart can't fix; extra='forbid' catches misspelled flags.
  • HealthCacheEntry — the poller reassigns a whole entry rather than mutating fields, so a corrupt debounce record can't be read back into a later poll cycle.
  • PendingVendorReviewRow — pins the "pick a vendor" dialog's row shape so a renamed DB column fails at model construction, not as a blank cell.
  • ServerStatus — the four-state tab vocabulary, validated where a fifth state would silently escalate a healthy server as stale.
  • ReportRowClass — the only shape a cat-* class may have, checked at the one place that writes it into a report file on disk.
  • RecategorizeRequest — a row id must be a whole number and an amount must be finite, because int(3.9) and Decimal('nan') both used to succeed and then quietly do the wrong thing.
  • Win10CacheEntry — the entry, not the value, is the presence sentinel, so a cache whose legal answers include None can actually cache one.
  • ConversationMessages — the one message path that bypasses ILettaGateway, where an unrecognised payload used to become an empty tab indistinguishable from a quiet agent.
  • CodexUsage / ClaudeUsage — the payload that decides whether the fleet's account gets swapped. An unreadable body used to classify as headroom; the claude side rendered it as a confident 5h 0% / weekly 0%. Now refused, and the refusal is deliberately worded so the dashboard does not call it a rate limit.
  • StandbyCredentials (new) — the parked second ChatGPT account. A bundle without account_id did not fail the "never park another account's token" guard, it disabled it, and the heal then overwrote the fleet's only spare credential with a stranger's single-use refresh token. One required field, chosen because its absence turns a guard off rather than raising; access_token left optional because a token-less bundle is what the heal path exists for.

How this plan reaches the dashboard

It is already wired in: dashboard.html has a #dashboard-refactor-plan-frame iframe pointing at /notes_plans_handoffs/dashboard_refactor_plan.html, behind the Dashboard Refactor tab under Project Plans. Live at https://desktop-2obsqmc.tailb8fc54.ts.net/.

A trap that looks exactly like a failed deploy: a tab switch in the dashboard only toggles a CSS class, so the iframe is fetched once, when the dashboard page itself loads. A dashboard left open all day keeps showing whichever revision of this plan it pulled at load time, however many times you redeploy. The frame carries data-refresh-on-show, and activateView in js/boot/view-navigator.js re-fetches marked frames every time their tab is opened. If a plan still looks stale, reload the dashboard page before suspecting the deploy — and confirm with curl -s <live>/notes_plans_handoffs/<plan>.html | grep <marker>, which asks the server rather than the browser.
