Where the typing earned its keep

Win10CacheEntry — and the probe that was never cached. The three caches were plain {'value': None, 'ts': 0.0} dicts, tested for freshness as value is not None and now - ts < TTL. That reads like "is there an entry?" but actually asks "is the entry's value non-None", and the two questions only agree while None is not a legal value.

For win10_docker_ok it is a legal value: the probe is deliberately three-state and None means "the SSH did not come back". So an unknown answer was written to the cache and then never once served from it — every health poll paid another 8-second SSH timeout against a box that had just finished proving it was not answering. The one case the cache exists for was the one case that had no cache, silently, because a slow dashboard looks like a slow network.

Making the entry the presence sentinel (None = never probed) separates the two questions. Frozen and replaced whole rather than mutated field by field, for the same reason HealthCacheEntry is. Measured on the live box against a real blackhole address: 8.01s, then 0.000s. ensure_win10_docker now invalidates that cache in a finally, so the newly-cacheable "unknown" cannot pin a recovered box in host_unreachable for the rest of its TTL.

Round 7's note said to check whether the torn-read the model prevents was reachable before reaching for Pydantic here. It was not — every read and write already held the lock. The model earns its place for a different reason than the one that was predicted, which is worth knowing before trusting the next prediction in this file.

ConversationMessages — the one untyped fetch path. Every message the tabs render arrives through ILettaGateway, which normalises the shape — except an isolated scan conversation, which comes back from letta_get as whatever json.loads produced. The hand-rolled unwrapping shrugged at all of it, and an unrecognised payload became []: identical on screen to an agent that has said nothing, so "the payload changed shape" and "there is nothing to show" rendered the same, and only one of them is a bug.

{'messages': None} was worse than ambiguous. .get('messages', fallback) returns the stored None rather than the fallback, because the key is present — so None, not a list, reached select_thoughts, and the failure landed several frames from its cause. Now validated at the boundary. Because the route calls cached_thoughts, the raise lands in the proxy's refresh thread, which logs it and keeps serving the last good value: a shape change costs a log line, not a 500 and not a blank tab. 

payload                    old behaviour        new behaviour
{'messages': None}      -> None                 refused: Input should be a valid list
{'data': [], 'total':0} -> []                   refused: neither 'messages' nor 'results'
'nope'                  -> []                   refused: not a list or object
[19 real messages]      -> 19                   accepted (checked live)

The bug the live verification found

Indicator #2 had never worked. win10_container_states ran ['ssh', …, host, 'docker', 'ps', '-a', '--format', '{{.Names}}|{{.Status}}']. But ssh does not take an argv the way subprocess does: it joins everything after the destination into one string and hands it to the remote login shell, which parses it again. On the far side | was read as a pipe and {{.Status}} as a command, so the probe exited 127 with {{.Status}}: command not found and no output.

Nothing raised. rc 127 is not an exception, so states simply came back empty — and an empty result is indistinguishable from "the box has no containers", which container_status_for renders as '', which the route then omits from the payload entirely. So the whole point of the feature — the exit code and restart count that tell you a server crashed (139 = OOM/segfault) or is crash-looping rather than merely stopped — was dead from the day it was written. A red server could have Exited (139) sitting one SSH away, unread.

Fixed in 5ae369aa by passing the remote command as one quoted argument. Verified live: rc 127 and no output before, all six containers after. A regression test pins the argv shape, because the failure is invisible from inside Python — only the remote shell sees it.

This is worth a moment. The bug survived every round of this refactor, a full test suite, and a working dashboard, because the feature failing looks exactly like the feature having nothing to say. It was found only because the round's verification step insisted on running the moved code against the real box and reading the output rather than checking that the endpoint returned 200. That is the argument for standing rule 7, in one artefact.

The injection bundles

Both modules take a frozen Collaborators dataclass that server.py builds per call. Per call is the whole point — build it at import and monkeypatch.setattr(server, 'letta_messages', …) lands on a name nothing calls any more, which is the trap that bit five earlier rounds.

  • win10_node keeps only the restart log — _log_restart and RESTART_LOG — because every other restart handler in server.py appends to it. mark_server_starting is not injected: it lives in monitoring/server_lifecycle.py, not in server.py, so importing it directly shares the same process-wide state rather than creating a second binding. Inject what stays behind in server.py; import what already has its own home.
  • message_views keeps letta_messages (the gateway shim), letta_get and _msg_age_seconds — the agent-activity poller also uses the last one.

One wrinkle worth copying: the thoughts proxy lives inside the moved module and calls its own loader, so the bundle cannot be a trailing keyword there. BackgroundResultProxy.get(key, *loader_args) forwards positionally, so a two-line adapter puts deps first for the loader while every public function keeps round 7's trailing deps= convention: 

def _load_thoughts(deps, agent_id, conversation_id):
    return letta_thoughts(agent_id, conversation_id, deps=deps)

_thoughts_proxy = BackgroundResultProxy(
    loader=_load_thoughts, refresh_seconds=3, name='thoughts')

A test asserts the deps bundle is not part of the proxy's cache key. It is rebuilt on every call, so keying on it would make every call a miss and defeat the proxy entirely — which would look like nothing at all, just a slow tab.

How to rank a cluster

The right question is: which names stay behind in server.py after the move? A name referenced only by the cluster travels with it and costs nothing. Counting every top-level name a cluster touches penalises exactly the clusters that are most self-contained. Run this from dashboard/ against the current file before choosing: 

import ast
from collections import defaultdict
src = open('server.py').read(); tree = ast.parse(src)
funcs = {n.name: n for n in tree.body
         if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef))}
top = set(funcs)
for n in tree.body:
    if isinstance(n, ast.Assign):
        for t in n.targets:
            if isinstance(t, ast.Name): top.add(t.id)
refs = defaultdict(set)              # name -> top-level funcs that reference it
for fname, node in funcs.items():
    for sub in ast.walk(node):
        if isinstance(sub, ast.Name) and isinstance(sub.ctx, ast.Load) \
                and sub.id in top:
            refs[sub.id].add(fname)

def deps(name):
    n = funcs.get(name)
    return set() if n is None else {
        s.id for s in ast.walk(n)
        if isinstance(s, ast.Name) and isinstance(s.ctx, ast.Load) and s.id in top}

names = {...}                        # the cluster you are considering
while True:                          # pull in what only this cluster uses
    ext = set().union(*(deps(n) for n in names)) - names
    travels = {x for x in ext if not (refs[x] - names)}
    if not travels: break
    names |= travels
stays = sorted(set().union(*(deps(n) for n in names)) - names)
lines = sum(funcs[n].end_lineno - funcs[n].lineno + 1 for n in names if n in funcs)
print(lines, 'lines |', len(stays), 'stay behind:', stays)

Round 7's version stopped at one level. The loop above takes the transitive closure, which matters: agent-registry measured 56 lines / 1 name at one level and 72 lines / 3 names closed, because the travellers had their own dependencies that the first pass never looked at.

Four caveats, all of them earned

  1. The script counts function bodies, so module-level constants that travel are free lines it does not credit — and the wrappers and explanatory comments left behind cost lines back. Round 8 measured 183 and removed 152 net.
  2. It cannot see http_app. It parses server.py and nothing else, so every srv.<name> call in http_app/get_routes.py and http_app/post_routes.py is invisible to it. Round 8 had seven names that looked cluster-internal and were in fact route dependencies. Always grep http_app/ for every name you plan to drop. The suite will not catch it: tests/http_app_harness.py stubs the service layer, so those tests pass against a name that no longer exists.
  3. It cannot tell you a name is mis-clustered. Round 8 measured the "Document Vision health" section at 83 lines with zero names left behind — an apparently free extraction. It is a mirage: that section is already extracted, and the 83 lines are the HEALTH_CHECKS registry and server_health, which sit under its header and are used by everything. Two more, in the table below, are named there. Grep every name you are about to move.
  4. Cluster membership is a judgement — widen or narrow the set and the numbers move.

Standing rules for every round

  1. Extract lowest-residual-coupling first, measured with the script above, not by eye. Then grep every name in your set — the script cannot tell you a name is mis-clustered.
  2. Grep http_app/ before dropping any name. The script parses server.py only, and the route ladders reach in through srv.<name> at call time. The HTTP tests stub the service layer, so they will not catch a missing name either. New in round 8, which had seven.
  3. Point new tests at the owning module, never at server. A re-export is a second binding; the moved code closes over its own module global, so monkeypatch.setattr(server, 'X', …) isolates nothing while looking exactly like it does. This has bitten five rounds running.
  4. Inject what stays behind in server.py rather than importing it, and resolve the bundle per call. Add a test that production wires the real collaborators, and one that proves the late binding. A dependency that already has its own module (mark_server_starting) is imported, not injected — injecting it would be ceremony, importing a server.py name would be a second binding.
  5. Import back only what is still called. Assert the dropped names are absent so dead re-exports cannot creep back, and assert the kept ones are the owning module's object.
  6. A fake must be pinned to the real thing it fakes. Where a dashboard module fakes a rol_finances object, add one test that runs the path unpatched against the real one — that boundary is sys.path-injected and entirely untyped. (See the round-6 postscript.)
  7. Deploy and verify against the real thing. Committing is not deploying, and a 200 is not a verification. For a backend-only change, call the moved code on the live box and read the output. Round 8 found a feature that had never once worked, in code that had passed every previous review, because rc 127 and "nothing to report" render identically. If the moved code writes, find a reversible way to watch it write — and if there is no reversible way, say so in this file rather than firing it or pretending it was checked.
  8. Every Pydantic model dumps to a plain dict so browser-facing JSON stays byte-identical, and keep a golden-payload test against the prior literals — error strings included.
  9. Reach for Pydantic where a wrong value is silent, not everywhere. The test that proves it earns its keep is usually the one showing the old code accepting garbage. And check the predicted defect is actually reachable: round 8's cache model was predicted for a torn read that could not happen, and earned its place for an entirely different bug.
  10. Stay out of js/ — unless the bug is there. A concurrent dashboard-boot.js refactor runs in parallel; an earlier round saw tests/test_project_plans.py fail on its edits, not ours. Confirm with git status js/ before blaming yourself. Broken deliberately in e28bd5fd: the stale-plan bug lived in js/boot/view-navigator.js and could not be fixed anywhere else. Round 8 touched nothing there.

  • PcMetric derives alert from level as a property, so a new level can't be added without deciding whether it blinks the tab.
  • ProbeResult.hard — suppresses the Restart button for failures a restart can't fix; extra='forbid' catches misspelled flags.
  • HealthCacheEntry — the poller reassigns a whole entry rather than mutating fields, so a corrupt debounce record can't be read back into a later poll cycle.
  • PendingVendorReviewRow — pins the "pick a vendor" dialog's row shape so a renamed DB column fails at model construction, not as a blank cell.
  • ServerStatus — the four-state tab vocabulary, validated where a fifth state would silently escalate a healthy server as stale.
  • ReportRowClass — the only shape a cat-* class may have, checked at the one place that writes it into a report file on disk.
  • RecategorizeRequest — a row id must be a whole number and an amount must be finite, because int(3.9) and Decimal('nan') both used to succeed and then quietly do the wrong thing.
  • Win10CacheEntry (new) — the entry, not the value, is the presence sentinel, so a cache whose legal answers include None can actually cache one. Before this, the slowest probe in the file was the only one that never hit its cache.
  • ConversationMessages (new) — the one message path that bypasses ILettaGateway, where an unrecognised payload used to become an empty tab indistinguishable from a quiet agent.

How this plan reaches the dashboard

It is already wired in: dashboard.html has a #dashboard-refactor-plan-frame iframe pointing at /notes_plans_handoffs/dashboard_refactor_plan.html, behind the Dashboard Refactor tab under Project Plans. Earlier revisions of this file claimed the opposite — that wiring it up was open housekeeping — and that claim was carried forward for several rounds without anyone checking dashboard.html.

A related trap, because it looks exactly like a failed deploy: a tab switch in the dashboard only toggles a CSS class, so the iframe is fetched once, when the dashboard page itself loads. A dashboard left open all day keeps showing whichever revision of this plan it pulled at load time, however many times you redeploy. The frame now carries data-refresh-on-show, and activateView in js/boot/view-navigator.js re-fetches marked frames every time their tab is opened. If a plan still looks stale, reload the dashboard page before suspecting the deploy — and confirm with curl -s <live>/notes_plans_handoffs/<plan>.html | grep <marker>, which asks the server rather than the browser.
