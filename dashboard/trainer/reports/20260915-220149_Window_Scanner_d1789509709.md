## Escalation (application defect — not Mazda)

The persistent FAIL on trace 568, even after the category was corrected to the exact matching payee-leaf id, is a **judge/rubric bug**, verified by reading source (no DB access used):

`agent_self_improvement/implementations/evaluation/category_plausibility.py`:
- `load_live_taxonomy()`'s SQL is `SELECT id, parent_id, name, is_report_category FROM categories ...` — it never selects `report_category_id`.
- `SnapshotTaxonomy.report_category_for()` walks only `parent_id`, testing `is_report_category` at each node; it never consults `report_category_id`.

Per `migrations/2026_07_28_002_backfill_report_flags.sql`, the Housing branch's reporting bucket is defined **only** via that override pointer (`UPDATE categories SET report_category_id = 300 WHERE id = 2` — node 2 itself is never given `is_report_category=1`; the comment literally says "its other children inherit via the walk (310/320/330/340/350 -> 2 -> 300)", but the walk that exists does not implement that inheritance). Consequence: `report_category_for()` returns `None` for category 331 (and for `330`/`2` and every other Housing-branch id reachable only through that pointer — also `110`, `240`, `358`, `400`, `364` per the same migration). Since `plausible = bool(expected and actual and expected[0] == actual[0])`, a `None` `expected` makes `plausible` False unconditionally — **even when `matched_category_id == category_id`, i.e. the merchant's own exact-match category was assigned.** This makes `category_plausible` spuriously and permanently fail for any Housing-branch (or similarly-pointered) category whose name happens to match the merchant string, no matter how correct the categorization is.
