## Wrapper defect diagnosed (recurring, not new)

This is not a one-off slip. The **identical** `doc_kind=unknown`-instead-of-`other`
transcription mistake, on the identical `classify_scan → doc_type=other` path, has now
been proposed and "activated" into the wrapper at least 8 times: proposals 99, 100, 112,
130, 133, 177, 230, and now 241/242 (rules 17, 18, 20, 23, 25, 41, 53 in `wrap-v073`'s
instruction text). Each cycle re-discovers the same bug, files a near-duplicate proposal,
gets gated through (safety/cost/regression/usefulness all "allow"), and is "activated" —
yet the mistake recurs on the next unsupported-document run regardless. Two candidate root
causes, in order of likelihood:
- **Prompt dilution**: `wrap-v073`'s instructions block is already ~9,000+ words of
  accumulated near-duplicate rules; a cheap mini model plausibly cannot reliably locate
  and apply the one relevant rule among 55+ others every time.
- **The proposal is prose-only** — nothing deterministic enforces `doc_kind :=
  classify_scan_output.doc_type`. A tool-level fix (have `record_trace`'s caller, or a
  thin wrapper around it, auto-populate `doc_kind` from the classifier's own structured
  output rather than trusting the LLM to retype it) would make this class of error
  structurally impossible instead of relying on the 9th prompt reminder to finally stick.

This is a **design observation for a human**, not something I'm escalating as a
`repo_path`-specific application bug — I don't have enough visibility into where
`record_trace`'s evidence assembly happens (agent-side prompt vs. tool schema) to write a
concrete `bug_description`/`failing_command`. Flagging it here so a human can decide
whether to consolidate/prune `wrap-v073`'s instruction block or add a deterministic
`doc_kind` derivation.
