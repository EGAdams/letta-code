## Wrapper defect diagnosed

Rather than switching to a robust programmatic approach immediately, she **hand-typed transaction rows into the HTML as literal Python tuples** to route around the shell errors. This introduced two independent defects, both present in the report she initially graded PASS:

1. **Fabricated data.** The hand-typed "ROKU FOR FUBO 8162728107 DE" row showed `-105.99`; the real statement JSON has that transaction at `-32.99`. The report also contained an entirely invented transaction, "IRS DIRECT PAY -2256.00" dated 2024-12-26, which does not exist anywhere in the 30-row source statement. This produced 29 report rows against only 28 real duplicate-matched expenses, so the fabricated row absorbed one of the 28 real expense IDs and misattributed its category.
2. **Wrong location.** The report was written under `incoming_scans/` instead of the statement's archive directory(ies).

The `hydrate_report_categories_from_db.py` / `audit_statement_reports.py` pipeline *was* actually invoked (not skipped), and it reported `ok:true` — but those scripts only check structural well-formedness (blank IDs, categorization coverage), not truth-to-source. A structurally valid report built from invented data still passed audit and judge_trace. This is the exact "audit PASS is not proof of correctness" trap the Trainer contract calls out.
